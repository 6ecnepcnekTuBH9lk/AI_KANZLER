# Архитектура первой версии

Приложение работает локально одним процессом FastAPI. Он раздаёт production-сборку React и API. Расчёты и классификация выполняются в двух фоновых потоках; HTTP-запрос загрузки возвращает идентификатор задания. SQLite хранит состояние и готовый результат, исходные XLSX и отчёты находятся на диске.

## Поток данных

`Upload → FileService → JobExecutor → module.service.run → result + sections → SQLite + XLSX → UI`

Модули возвращают один набор рассчитанных строк. Экспорт строится из него, затем те же строки сохраняются в БД. React форматирует числа, фильтрует и сортирует, но не рассчитывает бизнес-показатели. Схемы русских колонок коммерческого модуля задаются в `modules/merchandise/reporting.py` и передаются интерфейсу через API.

## Границы пакетов

| Пакет | Назначение |
|---|---|
| `backend/app/core` | Конфигурация, подключение БД, задания, обработка ошибок |
| `backend/app/shared` | SQL-модели, файловое хранилище, чтение Excel, история и выдача результата |
| `modules/merchandise/importers.py` | Роли, сезон, даты, семантическое сопоставление колонок |
| `planning.py`, `metrics.py` | Утверждённый план и расчёты факта/прогноза |
| `decisions.py` | Статус, причины, цена, вторая волна, действие и контроль |
| `history.py` | Контекст трёх встроенных исторических файлов |
| `modules/tnved/features.py` | Признаки изделия и ключ группировки |
| `alta.py`, `classifier.py` | Получение кандидатов, доказательства и трёхзначная проверка условий |
| `modules/*/reporting.py` | Коммерческий отчёт либо точечное изменение OOXML ТН ВЭД |
| `frontend/src` | Навигация, загрузки, прогресс, таблицы, графики, карточки |

Для нового модуля достаточно собственного router/service и регистрации в `main.py`; менять коммерческие формулы или классификатор ТН ВЭД не требуется. Фиктивных будущих модулей нет.

## Хранение

| Таблица | Данные |
|---|---|
| `files` | UUID, исходное имя, SHA256, размер, путь, модуль |
| `jobs` | Запуск анализа, входы, параметры, статус, прогресс, сводка, ошибка, путь отчёта |
| `analysis_rows` | Строки результатов по запуску и разделу, JSON-показатели |
| `merchandise_weekly` | Артикул, начало недели, вид значения, величина; одна строка на значение |
| `tnved_cache` | Сигнатура характеристик, код, время и доказательство Alta |
| `app_settings` | Основа хранения параметров; в первой версии активные настройки читаются из конфигурации |

Недельные поля в XLSX разворачиваются только при экспорте. В SQL нет отдельной колонки для каждой недели. Миграция `0001` содержит фиксированную схему, независимую от последующих изменений ORM. PostgreSQL потребует драйвер, URL и отдельную проверку миграций/переноса; сейчас проверена SQLite.

## Надёжность

- Входы записываются под UUID, исходные пользовательские файлы не меняются. Проверяются формат ZIP/XLSX, размер и отсутствие VBA.
- SQLite использует WAL. Результаты переживают перезапуск. Прерванные задания переводятся в понятную ошибку; автоматического продолжения посреди расчёта нет.
- Задания имеют состояния `queued/running/completed/failed`. Исключения попадают в журнал, интерфейс получает русское сообщение без traceback.
- Alta: HTTPS, тайм-ауты, ограничение частоты, повтор временных ошибок, отсутствие обхода авторизации. Кэш в памяти действует в рамках запуска; сохранённый код повторно проверяется по актуальной странице.
- Экспорт ТН ВЭД изменяет только нужные части ZIP; прочие части, включая рисунки и формулы, копируются побайтно. Формулы в колонке исходного кода сохраняются по умолчанию. При формулах в исходной колонке комментария создаётся отдельная колонка «Комментарий ТН ВЭД».
- API имеет пагинацию. UI получает все страницы выбранного раздела, затем фильтрует локально. Для очень больших наборов целесообразно перевести фильтры UI на сервер; текущий подход требует памяти браузера.

## Ограничения инфраструктуры

Один экземпляр сервера на одну SQLite-базу; несколько серверных процессов с общей очередью не поддерживаются. Нет отмены выполняющегося задания, корпоративного SSO, разграничения прав и автоматической очистки истории. Для ежедневной локальной работы эти функции не обязательны, для общего корпоративного размещения понадобится отдельный этап.
